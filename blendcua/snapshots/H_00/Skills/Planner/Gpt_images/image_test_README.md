# Image_test — view re-projection probe across three image models

How well can gpt-image-2 turn the single reference plate of a train task into the
front / side / top views a modeller actually needs? One folder per task, each
holding the copied `reference.*`, the generated plates, a `manifest.json` with the
exact prompt behind every plate, and a `contact_sheet.png` that lines them up.

Generated by [generate_views_gpt_image.py](generate_views_gpt_image.py) —
`model=gpt-image-2`, `images.edit`, `quality=medium`. 66 plates, all returned.

**[REVIEW.md](REVIEW.md) is the assessment** — every plate judged good or bad,
the ten re-prompted retries (`*_v2.png`, originals kept alongside), and what
wording made each one better.

```
python generate_views_gpt_image.py                        # all tasks, skip existing
python generate_views_gpt_image.py --only 09 18           # task-number prefixes
python generate_views_gpt_image.py --only 11 --jobs 02_side --force
python generate_views_gpt_image.py --sheets-only          # rebuild contact sheets
```

The key is read by `blendcua_core.load_api_keys()` from the file outside the repo;
nothing is written here.

## What was asked for

A front view only where the reference was not already front-on, plus side and top
everywhere. Four tasks needed a preparation pass first, whose output then became
the source image for the views after it:

| task | prep | why |
| --- | --- | --- |
| `08_desk_chair` | `00_isolate_desk`, `01_isolate_chair` | two objects in one plate |
| `13_domino_cascade` | `00_clean_side` | reference is a motion-blurred photo |
| `18_thors_hammer` | `00_upright_front` | reference is tilted diagonally |
| `19_human_thinker` | `00_clean_front` | reference is a Blender viewport grab |

## Results

Good on the first attempt, 52/56. The plates that stand out as directly usable as
modelling guides:

- **09_skull** — front, lateral and superior views all anatomically right, with the
  sutures carried through. The task asks for exactly this and gets it.
- **18_thors_hammer** — the tilt is removed cleanly and the head squares up; the
  side view correctly narrows the head to its striking face and the top view reads
  as the gold-framed rectangle.
- **14_sneaker** — front, top and a bottom view with a plausible tread pattern.
- **11_umbrella / 02_chess_staunton / 16_hourglass / 07_monstera_pot** — the top-down
  plates are the valuable ones: eight canopy panels, the rook's crenellation ring,
  the four column finials, the leaf rosette.
- **08_desk_chair** — the isolation splits the two objects cleanly, reconstructs
  what each was hiding from the other, and the six views off the isolates are
  consistent with each other.
- **13_domino_cascade** — the motion blur comes off and the spacing survives into a
  usable plan view.

### Where it needed a second pass

Four plates came back wrong first time and were re-prompted:

| plate | first attempt | what fixed it |
| --- | --- | --- |
| `04_datestone_1934/02_top` | returned the carved front face again | naming the camera position ("mounted on the ceiling") and saying explicitly that the numerals must not be visible |
| `06_iron_gate/02_top` | returned the gate face again | same |
| `11_umbrella/02_side` | closed the umbrella into a furled cone | "FULLY OPEN — do not close, do not furl", and asking for a 22.5° spin about the shaft rather than "rotate 90 degrees" |
| `12_tablecloth_drape/02_side` | near-duplicate of the front | asking for the near *corner point* to aim at the camera, instead of naming an angle |

The pattern in all four: the model resists a viewpoint from which the object's
recognisable face disappears. A top-down of a thin slab, or a rotation that hides
the hero surface, gets quietly replaced by the canonical view unless the prompt
says what must *not* be in frame.

A further ten plates were judged weak on review and re-prompted into `_v2`
files (originals kept). Eight improved, one was a wash, one traded faults — the
full breakdown, and the prompt wording that fixed each, is in
[REVIEW.md](REVIEW.md).

### Remaining weaknesses

- **Proportion drift.** `05_energy_can/01_side` rotated the label correctly but
  shrank the can to a thin rod, and `01_cardboard_box/02_side` came back taller
  than the box in its own front view. Scale is not conserved across a
  re-projection unless the prompt pins it — both are fixed in their `_v2` plates
  by stating the ratio explicitly. Treat these as guides for form and feature
  placement, not for measurement.
- **Detail invention.** `14_sneaker/03_bottom` and `18_thors_hammer/02_top` are
  plausible rather than derived — the reference never showed those surfaces.
- **Rotationally symmetric objects** (`03_wine_glass`, `02_chess_staunton`) return a
  side view all but identical to the front, which is correct, and a genuinely
  informative top view.

## Re-running against gpt-image-2.5

OpenAI shipped GPT-Image-2.5 in two variants and both are worth testing here,
since the failure this probe measures is a *viewpoint* failure, not a fidelity
one, and the two variants trade off differently:

| model id | what it is |
| --- | --- |
| `gpt-image-2.5-flare` | the everyday one: better than gpt-image-2 at roughly half the latency |
| `gpt-image-2.5-sunburst` | the premium one: tighter control across edits |

Same script, same 66-plate plan, same prompts. Only `--model` and the output
folder change, so the original `baseline/` run stays exactly as it was and the
three runs are directly comparable.

```
python generate_views_gpt_image.py --model gpt-image-2.5-flare    --probe
python generate_views_gpt_image.py --model gpt-image-2.5-flare
python generate_views_gpt_image.py --model gpt-image-2.5-sunburst --probe
python generate_views_gpt_image.py --model gpt-image-2.5-sunburst
```

`--probe` runs one plate, prints what the API accepted and what it cost, and
stops. Do it first for each new model: 2.5 is new and its parameter surface is
not guaranteed to match gpt-image-2, so the call sends `quality`, `background`
and `output_format` and drops whichever one the API rejects, recording the drop
in the manifest. The probe is how you find that out for one plate's worth of
money rather than 66.

Everything lives under this folder — the scripts at the top, one subfolder per
run:

```
baseline/       gpt-image-2, the original run, unchanged
flare/          gpt-image-2.5-flare
sunburst/       gpt-image-2.5-sunburst
compare/        the comparison, written by compare_runs.py
hammer_trial/   the 18_thors_hammer prompt trial, 3 prompts x 3 models
```

Each run also writes `run_summary.json` at its root: calls, ok count, seconds,
tokens and dollars.

### The comparison

```
python compare_runs.py              # REPORT.md, summary.csv, per_task.csv
python compare_runs.py --sheets     # plus sheets/<task>.png, one row per model
```

`--sheets` is the one that answers the question this probe actually asks. Cost
and latency come out of the manifests, but whether 2.5 gets the top-down view
of a thin slab right, where gpt-image-2 kept returning the carved front face,
is something you have to look at. The sheets put the same plate from all three
models on one row above each other.

**One gap in the cost comparison.** The original run predates usage capture, so
`baseline/` has timings (mean 33.3 s per plate, 2132 s over 64 calls) but no
token counts and therefore no dollar figure. If you want a priced baseline
rather than an inferred one, re-run it into a separate folder so the original
stays put:

```
python generate_views_gpt_image.py --model gpt-image-2 --out baseline_priced --force
python compare_runs.py --roots baseline_priced flare sunburst
```

Published rates are in `PRICES` at the top of the generator, taken from the
pricing page on 2026-09-08: gpt-image-2 at $2.50/$4.00 in and $15.00 out per 1M
tokens, both 2.5 variants at $5.00/$8.00 in and $30.00 out. The two 2.5
variants are priced identically per token, so whatever cost difference shows up
between Flare and Sunburst is a difference in how many tokens they spend.

### The API key

`blendcua_core.load_api_keys()` reads a single `KEY=value` file and refuses to
read one from inside the repo. The default location is `blendcua.env.txt` in
your home directory, so on this machine:

```
/Users/gauravjoshi/blendcua.env.txt        # one line: OPENAI_API_KEY=sk-...
chmod 600 /Users/gauravjoshi/blendcua.env.txt
```

Anywhere else works too, pointed at with `BLENDCUA_KEY_FILE`, as long as it is
outside `Blenduse/`. An `OPENAI_API_KEY` already exported in the shell wins over
the file, so a one-off key does not need the file at all.
